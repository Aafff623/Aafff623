# Tech Stack 3D Q 版骑士 GIF 重设计规划

状态：规划完成，尚未制作或替换正式资产。

## 1. 目标

将 Tech Stack 右栏现有的二维吉祥物 GIF 改为 3D Q 版骑士循环动画。新动画需要比现有版本更成熟，但仍保留轻量、友好和容易辨认的角色气质。

本次工作只确定素材处理、动作编排、转场、明暗主题、编码和接入方案。制作阶段开始前，不覆盖 `assets/mascot.gif`，也不修改 `README.md` 或 `preview-profile.html`。

## 2. 现有接入基线

当前 Tech Stack 模块在 `README.md` 和 `preview-profile.html` 中使用相同结构：

- 表格左右栏比例为 `75% / 25%`。
- 右栏图片显示宽度为 `90%`。
- 正式资源路径为 `./assets/mascot.gif`。
- 当前 GIF 为 `360x360`、18 fps，循环约 4.5 秒，文件约 1 MB。

首版 3D 动画沿用这些尺寸和布局。先把角色动画本身做好，再判断右栏宽度是否需要调整，避免资产和布局同时变化后难以定位问题。

GitHub README 不执行 CSS 动画、JavaScript 或视频。最终交付必须是预合成 GIF。明暗主题切换只能依靠紧凑的 `<picture>` 和 `<source media>` 结构。

## 3. 素材审计

源素材位于：

`./.scratch/chibi-knight-import/chibi_knight_5_images/`

5 张图片均为 `1254x1254` PNG、`Format24bppRgb`，没有 Alpha 通道。源图不能直接叠放到不同背景，需要先抠出角色和特效，生成带 Alpha 的中间帧，再分别合成亮色和暗色版本。

### 3.1 文件与实际动作

| 原文件 | 实际画面 | 动画内部名称 | 用途 |
| --- | --- | --- | --- |
| `01_initial_3d_chibi_knight.png` | 准备持剑 | `pose-01-ready` | 循环起点和回环终点 |
| `02_scene_01_sword_slash.png` | 闭眼静息、双手祈剑 | `pose-02-rest` | 蓄力前的安静停顿 |
| `03_scene_02_energy_thrust.png` | 向右能量突刺 | `pose-03-thrust` | 第一次速度峰值 |
| `04_scene_03_resting_pose.png` | 旋转挥斩 | `pose-04-spin-slash` | 攻击动作延续 |
| `05_scene_04_victory_pose.png` | 腾空庆祝 | `pose-05-victory` | 情绪峰值和循环收束 |

`02` 和 `04` 的文件名与实际动作相反。制作脚本和帧清单必须使用动画内部名称，不能继续依赖原文件名判断动作。

### 3.2 一致性问题

角色主体基本一致，可以组成同一段循环，但不能直接使用长时间 crossfade。主要问题包括：

- 各图的头脸尺寸、身体比例和画面落点不同。
- 盔甲分格、剑格和局部材质存在细微漂移。
- 剑的位置和方向变化很大，长叠化会产生双剑和残肢。
- 攻击帧的光效范围不同，统一脚底线会破坏 03、04 的构图。
- 05 是腾空姿势，强行落地会削弱庆祝动作。

因此，动画以脸中心为主锚点。脚底只用于检查稳定感，不作为所有帧的硬性对齐线。

## 4. 动作叙事

推荐循环顺序：

`准备持剑 → 静息祈剑 → 能量突刺 → 旋转挥斩 → 腾空庆祝 → 准备持剑`

这条动作链有清楚的起伏：先建立角色，再短暂停顿，随后连续攻击，最后庆祝并回到准备姿势。攻击帧不单独解释技能名称，避免动画比 Tech Stack 内容更抢眼。

## 5. 画布、裁切与对齐

### 5.1 输出规格

- 画布：`360x360`。
- 帧率：18 fps。
- 色彩：sRGB。
- 循环：无限循环。
- 角色主体不得触碰画布边缘，剑光可以接近边缘，但不能出现硬裁切。

### 5.2 对齐规则

1. 先在高分辨率中间画布完成抠图、缩放、定位和特效，再统一缩小到 `360x360`。
2. 以脸部中心作为第一锚点，建议初始目标位置为画布水平中心、垂直方向约 35%。实际制作可在 2% 到 3% 范围内微调。
3. `pose-01-ready` 进入 `pose-02-rest` 时缩小约 7% 到 8%，同时按脸中心和脚底视觉位置校正。
4. `pose-03-thrust` 和 `pose-04-spin-slash` 保留攻击方向，不为了统一脚底而压缩动作幅度。
5. `pose-05-victory` 保留腾空高度。回环时通过放射线收束和白闪遮挡位置变化。
6. 每个静态停留段只允许 1% 到 1.5% 的缓慢缩放和最多 2 px 的垂直漂移。不要模拟独立肢体运动，单张源图无法支持可靠的骨骼补间。

## 6. 时间轴基线

首版使用 73 帧，总时长约 4.06 秒。这个长度与现有 GIF 接近，也能让每个姿势看清楚。

| 帧范围 | 帧数 | 内容 |
| --- | ---: | --- |
| 0-11 | 12 | `pose-01-ready` 停留，轻微呼吸缩放 |
| 12-15 | 4 | 01 → 02 短叠化 |
| 16-27 | 12 | `pose-02-rest` 停留，动作趋于安静 |
| 28-29 | 2 | 02 → 03 金色闪白和向右能量擦除 |
| 30-39 | 10 | `pose-03-thrust` 停留，能量尾迹快速衰减 |
| 40-43 | 4 | 03 → 04 在光效遮挡下短叠化 |
| 44-53 | 10 | `pose-04-spin-slash` 停留，弧光继续旋转后衰减 |
| 54-58 | 5 | 04 → 05 特效桥接，中间 3 帧叠化角色 |
| 59-70 | 12 | `pose-05-victory` 停留，放射线缓慢减弱 |
| 71-72 | 2 | 05 → 01 放射线收束、白闪、切回起点 |

静态姿势可在 8 到 14 帧范围内调整。角色图像的连续叠化不得超过 4 帧，约 222 ms。转场段可以占 5 帧，但首尾帧只能用于特效桥接，不继续叠加两个人物姿势。若节奏需要改变，优先调整停留帧，不延长叠化。

## 7. 逐段转场设计

### 7.1 准备持剑 → 静息祈剑

使用 4 帧短叠化。先将准备姿势缩小约 7% 到 8%，再按脸中心和脚底视觉位置对齐。背景亮度保持稳定，避免第一段就出现强闪光。

验收重点：头部不能突然放大，剑不能在画面中保留两把超过 2 帧。

### 7.2 静息祈剑 → 能量突刺

不能裸 crossfade。用 2 帧完成金色闪白和向右能量擦除，总时长约 111 ms：

1. 中心剑光快速增亮，同时让向右扩张的金色能量带覆盖手臂和剑的位置变化。
2. 在亮度峰值切入突刺帧，随后让尾迹在姿势停留段内衰减。

验收重点：不能看到闭眼静息姿势和突刺姿势长时间重叠，也不能出现双头或多肢。

### 7.3 能量突刺 → 旋转挥斩

使用 4 帧短叠化，但叠化发生在特效遮挡下。让直线能量带扩张并弯成环形弧光，借弧光遮住剑向和身体角度的变化。

验收重点：直线能量和圆弧必须有连续方向，不能像两个无关特效突然叠在一起。

### 7.4 旋转挥斩 → 腾空庆祝

这是素材中最适合直接衔接的一段。使用 5 帧特效桥接，只有中间 3 帧叠化角色。旋转弧光先在亮度峰值过曝，再接到庆祝帧的放射线。角色可以向上移动少量距离，但脸中心的水平位置保持稳定。

验收重点：腾空动作应显得主动上扬，而不是角色突然换了尺寸。

### 7.5 腾空庆祝 → 准备持剑

不能裸 crossfade。使用 2 帧回环遮罩，总时长约 111 ms。放射线向角色中心收束并形成短促白闪，在最亮帧切回准备姿势。循环首帧继续保留少量余光，避免 GIF 回到第 0 帧时明显卡顿。

验收重点：连续播放 5 个循环时，观察者不应轻易指出回环切点。

## 8. 亮色与暗色版本

输出两套预合成 GIF，不使用 GIF 的二值透明边缘。二值透明容易在头发、盔甲高光和金色能量周围产生锯齿或白边。

### 8.1 亮色版本

- 最终路径：`./assets/mascot.gif`。
- 背景基准：GitHub 亮色页面的近白色，首选 `#ffffff` 或经实页对比确认后的浅灰。
- 保留柔和的地面阴影，但不能形成明显的方形卡片边界。
- 金色特效的最亮区域仍要保留层次，不能整片烧成纯白。

### 8.2 暗色版本

- 最终路径：`./assets/mascot-dark.gif`。
- 背景基准：GitHub 默认暗色附近的 `#0d1117`。
- 重新合成角色边缘，不能把亮色版本直接整体压暗。
- 降低大面积白闪的峰值面积，保留短促亮度变化，避免暗色页面中刺眼。
- 地面阴影改为低亮度环境光和微弱金色反射，不能保留灰黑色脏边。

GitHub 有多种暗色主题，单张预合成 GIF 无法匹配所有背景。验收时优先保证默认亮色和默认暗色不出现明显方框，并检查边缘在其他主题下是否仍可接受。

## 9. 中间资产与候选文件

原始图片继续保留在 `.scratch`，不复制到 `assets/`。建议制作目录：

```text
.scratch/mascot-3d/
├── manifest.json
├── mattes/
├── aligned/
├── frames-light/
├── frames-dark/
├── mascot-light.candidate.gif
├── mascot-dark.candidate.gif
└── preview.html
```

`manifest.json` 记录原文件、动画内部名称、缩放、脸中心锚点、位置偏移和每段帧数。这样可以重复渲染两种主题，而不是手工移动每一帧。

候选 GIF 通过验收前，不写入 `assets/mascot.gif` 或 `assets/mascot-dark.gif`。

## 10. GIF 编码预算

推荐基线：

- `360x360`，18 fps，73 帧，无限循环。
- 使用一套经过帧差优化的全局调色板。
- 首轮从 96 色开始测试。盔甲渐变或暗色光晕出现断层时，可提高到 128 色。
- 平坦背景优先不抖动。暗色光晕出现色带时，只使用轻量 ordered dithering，避免噪点导致体积明显上升。
- 目标文件大小：单个 GIF 不超过 1.5 MB。
- 可接受上限：单个 GIF 不超过 3 MB。超过上限时先减少无变化帧和特效噪点，不先降低画布尺寸。

编码后必须检查实际帧率、总帧数、循环标志、文件体积和最后一帧到第一帧的衔接。不能只看导出命令是否成功。

## 11. README 接入方案

验收后，保持 Tech Stack 的 `75% / 25%` 表格和右栏 `90%` 显示宽度。右栏图片改为以下紧凑结构：

```html
<picture>
<source media="(prefers-color-scheme: dark)" srcset="./assets/mascot-dark.gif">
<img src="./assets/mascot.gif" width="90%" alt="3D chibi knight cycling through sword poses">

```

同样的结构需要同步到 `preview-profile.html`。实际嵌入 `<table>` 时，`<picture>` 内部和相邻 table 标签之间不能插入空行，否则 cmark-gfm 可能提前终止 raw HTML block。

接入后使用 `gh api markdown` 验证 GitHub 渲染结果，并分别检查亮色和暗色模式。资源路径保持相对路径，不使用本机绝对路径。

## 12. 验收标准

### 12.1 动画

- 动作顺序与规划一致，循环时没有错序或停顿。
- 连续播放 5 个循环后，05 → 01 的切点不明显。
- 任何转场都没有持续可见的双剑、双头、多肢或模型融化感。
- 脸中心稳定，静态段没有超过 2 px 的无意义抖动。
- 攻击帧的剑和主要能量轮廓没有被画布硬裁切。
- 角色在右栏缩放到实际显示尺寸后，脸、剑和动作仍能辨认。

### 12.2 主题

- 默认亮色模式下没有明显白色方框边界。
- 默认暗色模式下没有白边、脏边或整块亮色底。
- 暗色版本的白闪不会长时间占据画面。
- 两个版本的动作帧、节奏和构图一致，只改变背景和必要的光效强度。

### 12.3 技术

- 两个 GIF 均为 `360x360`、18 fps、无限循环。
- 单个文件目标不超过 1.5 MB，最高不超过 3 MB。
- README 和本地预览使用相同的相对资源路径和 `<picture>` 结构。
- `gh api markdown` 渲染后，Tech Stack 表格没有断裂或掉出 raw HTML block。
- `git diff` 只包含已批准的资产与接入改动，不混入其他文件删除或无关格式化。

## 13. 实施步骤

1. 为 5 张源图建立 `manifest.json`，用内部动作名称解除原文件名歧义。
2. 抠出角色、武器、特效和必要阴影，生成高分辨率 RGBA 中间素材。
3. 以脸中心为主锚完成统一裁切和缩放，先输出静态 contact sheet 检查角色一致性。
4. 按 73 帧时间轴制作位置补间、微呼吸和五段转场。
5. 从同一套 RGBA 帧分别合成亮色和暗色帧序列。
6. 将候选 GIF 和独立预览页输出到 `.scratch/mascot-3d/`，不覆盖正式资产。
7. 在 Tech Stack 实际列宽下检查亮色、暗色和连续循环，并记录需要调整的帧段。
8. 压缩候选文件，复查帧数、帧率、循环标志、颜色断层和文件体积。
9. 用户确认后，将亮色版本写入 `assets/mascot.gif`，新增 `assets/mascot-dark.gif`，再同步修改 `README.md` 与 `preview-profile.html`。
10. 使用本地预览和 `gh api markdown` 做最终验证。

## 14. 回滚方案

规划和候选制作阶段不覆盖现有 `assets/mascot.gif`，因此这两个阶段不需要回滚正式页面。

正式接入后若出现渲染、体积或主题问题，回滚内容限定为：

1. 恢复上一版 `assets/mascot.gif`。
2. 删除或停止引用 `assets/mascot-dark.gif`。
3. 将 README 和本地预览的 `<picture>` 恢复为原来的单 `<img>`。

回滚时不要改动 Tech Stack 左栏内容、表格比例或仓库中无关的资产状态。
